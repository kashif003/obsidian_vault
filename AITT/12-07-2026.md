
1. collect.py:
- **[1] Connects to MQTT** — `create_mqtt_client()` ([collector.py:18](vscode-webview://1hlttc4dovpmrl6bb3l1j179gp5en062okd3mtdoes4snbp82obl/collect/collector.py#L18))*. Reads `MQTT_HOST`/`MQTT_PORT` from env vars (defaults `localhost:1883`). Retries with exponential backoff (5s → 60s cap) if the broker isn't reachable yet* — this matters because in Docker Compose the collector container can start before the broker is ready.
    
- **[2] Reads CSV files via SimPy — but concurrently, not one at a time.** `main()` spawns **one `csv_source()` process per CSV file** found in `data/wind_farm_B/` ([collector.py:144](vscode-webview://1hlttc4dovpmrl6bb3l1j179gp5en062okd3mtdoes4snbp82obl/collect/collector.py#L144)). Each process reads its file row-by-row with `csv.DictReader` (semicolon-delimited), sleeps 0.1s between rows to simulate a live feed, tags the row with `row_index`/`csv_name`, and **pushes it into a shared `simpy.Store`** (an in-memory queue) — it doesn't process the row itself.
    
- **[3] A separate `writer()` process consumes from that queue and normalizes each row.** This is the part your notes call "stores in dict format," but it's not persistent storage — it's an in-memory reshaping step done fresh per row, right before publishing. For each row: *metadata columns (`time_stamp`, `asset_id`, `id`, `train_test`, `status_type_id`) are dropped, and the rest are split on the **last underscore** into `sensor_name` + `metric` (e.g. `power_58_avg` → sensor `power_58`, metric `avg`), grouped into `{sensor_name: {metric: value, ...}}`, with values cast to `float`* where possible.
    
- **[4] Publishes to MQTT, per sensor group, not per row.** Since one row can contain multiple sensors, `writer()` publishes **one MQTT message per sensor** extracted from that row. Topic is `windfarm/{asset_id}/{sensor_name}`, QoS 1 (at-least-once), payload is JSON with `id`, `sensor`, `asset_id`, `time_stamp`, `values`, `published_at`. It also blocks/retries if the client is momentarily disconnected before publishing.

**Medallion Architecture**
+ data design pattern (popularized by Databricks) used to logically organize data.
+ GOAL: incrementally improve the quality and structure of data as it flows through three distinct layers.
	1. The Bronze Layer (Raw Data): data is loaded(from kafka etc) as it is, without any change.
	2. The Silver Layer (Cleaned and Conformed): The raw Bronze data is filtered, cleaned, and deduplicated.
	3. The Gold Layer (Curated for Business): The clean Silver data is aggregated and modeled to answer specific business questions

	**Implementation**:
	1. store the data on cheap cloud object storage (like AWS S3, Google Cloud Storage, or Azure Data Lake).
	2. transform the data using Apache Spark, Databricks, or Apache Flink.

	*Additionally:* You need a scheduler to ensure the data moves in the correct order. **Apache Airflow**, **Dagster**, or **dbt**
